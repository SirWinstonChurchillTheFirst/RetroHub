# ui-shell

## Summary
MonHub's UI shell is one Avalonia 11.3.22 window (MainWindow : HubWindow) built from three layers: a theme-swappable decoration layer (TemplatedControl slots Hub.Backdrop / Hub.RailIdentity / Hub.RailDeco), a left/right "rail" of RadioButton menu entries, and a PageHost Grid inside a themable "screen frame" ContentControl. Each page is a UserControl created lazily by string key ("start", "games", ...), kept in a Dictionary, and swapped by visibility. Nothing is unloaded. The other pages are built in the background at ApplicationIdle after the first activation, so the first click has no stutter. A page change is a 170 ms fade plus a 10 px upward slide (Avalonia Animation on Opacity and TranslateTransform.Y, CubicEaseOut), skipped when motion is Off. Theming is token-based: Themes/Base.axaml defines about 120 `Hub.*` tokens (brushes, CornerRadius, Thickness, Double, Boolean, Int32, FontFamily) plus every ControlTheme (Hub.Key, Hub.Nav, Hub.Card, Hub.Panel, Chrome.Button, Hub.DialogWindow ...), all referenced through DynamicResource. HubThemes.Apply then swaps one merged ResourceDictionary (Themes/<id>.axaml loaded via AvaloniaXamlLoader), copies tokens into the SimpleTheme stock brush keys, and flips RequestedThemeVariant. A theme can override whole ControlThemes or templates (the Game Boy theme replaces Hub.Nav/Hub.Card with a blinking pixel cursor). The window chrome is custom on Windows: ExtendClientAreaToDecorationsHint + NoChrome + a 34 px title-bar hint keep the OS frame (snap, resize, shadow, rounded corners), while MonHub draws its own drag area and minimize/maximize/close buttons (Chrome.Button / Chrome.Close). Linux gets SystemDecorations.None plus custom resize grips. Dialogs are HubWindow subclasses with a synchronous ShowDialog() built on a nested DispatcherFrame, and a themed MessageBox/Choose replacement is included. Motion has three levels (All/Calm/Off) plus a "follow Windows" default read through SystemParametersInfo(SPI_GETCLIENTAREAANIMATION). The Ambient.Animation attached property runs looping XAML Animations only when the element is visible and its window is active, not minimized and not blocked by a dialog; SpriteAnimator follows the same rules for frame-strip sprites on Background-priority DispatcherTimers. There is NO controller/gamepad navigation of the UI at all. XInputGetState (xinput1_4.dll) and joyGetPosEx (winmm.dll) appear only in Controls.cs (which is emulator input-binding settings, not UI controls) to detect a pad and to capture a button for remapping (polled every 40 ms in EmulatorsPage). Keyboard handling is minimal: Tab cycling in the Nav StackPanel, :focus-visible styles on a few control themes, and window-level tunnel KeyDown handlers in TourOverlay and EmulatorsPage. The Porygon tour (TourOverlay) is a reusable coach-mark overlay: a CombinedGeometry shade with a hole, an accent frame, and a card positioned below/above/right/left of the target with a pointing tip. Performance lessons (PERFORMANCE.md, comments in themes) focus on avoiding blur/drop-shadow effects near animated content, never animating by writing app resources, pausing loops when they can't be seen, keeping big backdrops static, and swapping themes as one dictionary.

## Pitfalls
- No controller support for UI navigation exists anywhere. XInput (xinput1_4.dll XInputGetState) and winmm joyGetPosEx are used only in Controls.cs to detect a pad and capture one button for remapping (EmulatorsPage polls PressedPad every 40 ms at DispatcherPriority.Input). RetroHub needs a new input layer (an SDL2/SDL3 GameController via a binding, or XInput + Windows.Gaming.Input) that turns pad events into focus moves (KeyboardNavigationHandler / FocusManager / custom spatial navigation), plus repeat timing and a 'focus only when window active' rule.
- Controls.cs is misnamed for this purpose: it is emulator input-binding config (Qt key codes, melonDS/mGBA/Azahar ini/toml writers), not custom UI controls. MonHub's only custom controls are SpriteView (GameLook.cs), TourOverlay, GameScreen and the HubWindow base.
- Focus visuals are weak: almost every ControlTheme sets FocusAdorner={x:Null}, and only Hub.Key (Face border), Hub.Nav (cursor opacity), CheckBox and TextBox:focus have focus styles. Hub.Card (the game list item), Hub.Tile, Hub.Chip, Hub.Ghost and Hub.RailMini have NO :focus-visible style, so a controller-driven list would show no cursor. Add a FocusRing token and :focus / :focus-visible styles everywhere, and consider scaling or a glow-free outline for the TV/10-foot view.
- Keyboard handling is ad hoc: window-level tunnel KeyDown handlers (TourOverlay L81, EmulatorsPage L31) swallow Tab/arrows/Space while active. There is no central input router or back-stack, and the Esc/Back semantics exist only per dialog (IsCancel). RetroHub should centralise the actions (Accept/Back/Menu/PageLeft/PageRight) in one router.
- HubWindow.ShowDialog() is synchronous through Dispatcher.UIThread.PushFrame (nested message loop), and HubWindow.Wait() blocks on file pickers the same way. That is convenient for WPF-ported code, but nested frames are re-entrancy hazards (see the MenuItem replay and _reporting guards needed in App). Prefer async ShowDialog<T> or in-window overlay dialogs for RetroHub.
- Compat.cs adds global usings that alias WPF names (FrameworkElement=Control, UIElement, DependencyObject, BitmapSource=IImage, Brush=IBrush) and extension properties (Visibility, ToolTip, ActualWidth). These are porting crutches; don't copy them into a fresh Avalonia codebase.
- DESIGN.md and PERFORMANCE.md are partly stale WPF documents: they reference Themes/*.xaml, 'WPF updates everything', DrawingBrush CachingHint="Cache", Timeline.DesiredFrameRate and DropShadowEffect. None of those are used in the Avalonia code (grep finds no DesiredFrameRate/CachingHint). PERFORMANCE.md's title even says 'der Randomizer'. The lessons still hold, but the API names don't map 1:1.
- AvaloniaUseCompiledBindingsByDefault=false in MonHub.csproj means reflection bindings. RetroHub should enable compiled bindings (x:DataType) for big libraries.
- Virtualization: the game list (Pages/LibraryPage.axaml L82) is a ListBox whose Hub.List template keeps ItemsPresenter + ItemsPanel, so the default VirtualizingStackPanel stays, but rows are 68 px list cards. A grid of cover art (thousands of games) needs a virtualizing wrap/grid layout (ItemsRepeater with UniformGridLayout or a VirtualizingWrapPanel package); MonHub's WrapPanels are non-virtualizing and only used for small sets.
- Ambient.Runner: setting Ambient.Animation creates a new Runner each time and never disposes the old one. Each running Runner also keeps a 700 ms DispatcherTimer polling IsEffectivelyVisible. That is fine for a handful of theme decorations, but don't use it per list item.
- MainWindow subscribes LayoutUpdated -> PlaceGame (fires after every layout pass); it is guarded by equality checks. Avoid heavier work in LayoutUpdated.
- Enter() page animation uses RunAsync without cancellation. Rapid page switching can overlap animations (harmless with FillBehavior defaults, but add a CancellationToken per page for controller fast-scrolling between tabs). It relies on Avalonia auto-creating a TransformGroup when RenderTransform is null, and HubAnim.Press skips buttons that already have a RenderTransform. Keep the two systems from fighting.
- The custom maximize button means no Windows 11 Snap Layouts flyout on hover (that requires WM_NCHITTEST HTMAXBUTTON handling). The caption buttons are plain Avalonia Buttons.
- WindowFit and PrimaryScreen() use Screens.Primary only, which gives wrong clamps on multi-monitor setups where the window opens on a secondary display.
- PERFORMANCE lessons to carry over: no BlurEffect/DropShadowEffect around anything that changes (use hard offset Borders); never animate by writing Application.Resources (it walks all windows' trees, and a per-frame write cost 0.19 to 0.81 ms at render priority, above input); big backdrops must stay static (rotating C-Gear rings behind text cost 34% of a core on WARP vs ~8%, see cgear.axaml L283-285 comment); animate only element-local properties (Image.Source, Opacity, RenderTransform); run timers at DispatcherPriority.Background; stop everything when minimized, inactive or dialog-blocked; debounce previews (350 ms) and resize-driven placement (120 ms).
- Pokemon-specific coupling not to copy: Porygon/PMD portraits and sprites (CC BY-NC, non-commercial only), the SpriteData.g.cs catalogue, team/badge/Nuzlocke DataTemplates and styles (Hub.TeamSlotTemplate, Ellipse.badge, Hub.Strike, Border.teamslot), ScreenLayout.cs (DS/3DS-specific: melonDS/DeSmuME/Azahar config), Txt.ForLinux DeSmuME text hacks, theme names and taglines (Kanto/C-Gear/Lavandia), and hardcoded German-first strings.
- The theme 'StandardControls' copy writes resolved token values into app.Resources (static copies). That is correct only because it re-runs on every Apply; don't call Apply per frame or per keystroke (MonHub debounces the custom background preview).
- The rule from DESIGN.md: a token must never share its key with a ControlTheme/style key, or the theme dictionary's value hides Base's style. Also use full FontFamily values (with fallbacks) for font tokens, not StaticResource aliases.
